## Threat model

Any account that can sign in is assumed hostile. It controls its Tumble client's configuration (an
OpenAI-compatible provider pointed at its own server reports any usage, custom model info sets any price, a custom
mode any name, task ids are generated by the client) and can send hand-made HTTP and socket.io traffic. It must not
be able to make another account's or an organization admin's page fail, show wrong figures or run unbearably slow,
corrupt another account's stored data, exhaust the server's memory or the database pool, or stop the upgrade. Harm to
its own figures is acceptable; a 500 on its own requests ranks below harm to others but is still worth closing.

Four read-only audits of the stack (numbers, strings, resources, cross-user) found the problems below in code older
than the stack. Each was reproduced by a test before it was fixed; the test fails without the fix (the mutation is
named with each test).

## Fixes

**1. Links between two accounts' tasks** (`task_tree.record_relation`, `adopt_from_relations`,
`link_pending_children`). A link was stamped whoever owned the two tasks. With an event naming another account's
task id, an account could hang that account's run under one of its own (the run vanished from its owner's list and
from the organization's quality panel), fold one of their runs into another (their stored run totals changed), steal
a subtask waiting for its parent, or put its own task under theirs (its breadcrumb showed their title, run cost and
quality). A link is now stamped only when the relation was sent by the owner of both tasks, at all three moments the
tree is built. `record_relation` takes the sender as a required argument. The relation itself is still stored (it is
the record of what telemetry said) and stays inert. Test: `test_bridge_task_tree.py::test_a_link_naming_another_accounts_task_moves_nothing`
(three owner pairs, each with the event, the child row or the parent row first); mutations: the owner condition
dropped from each of the three functions, each red.

**2. A completion naming another account's task** (`model_attribution.note_completion_model`). The lookup was by task
id only, so a completion with a new model id for someone else's task rewrote that task's row: its `updated_at`
jumped to now, the task moved to the top of its owner's list, into date filters and the quality panel's period, and a
retention policy keeping the newest N tasks then deleted a genuinely recent task of the owner. The lookup now
requires the sender to own the task. Test: `test_model_attribution.py::test_a_completion_naming_another_users_task_leaves_its_row`
(red without the condition).

**3. One task's card stopped every account's recall** (`recall_cards`). The background rebuild takes the 100 oldest
dirty tasks of all accounts, builds them in one transaction and commits once. A completion text with a NUL or a
lone surrogate (escaped in the stored JSON, decoded again for the card) made Postgres refuse the card, and a text
that is no string made the card layout raise; the batch rolled back, the poisoned task stayed first in the queue, and
no account's card was built again. Now `_text` drops the two characters Postgres' text cannot hold and reads a
non-string text as empty, and each card is built inside a SAVEPOINT (as retention sweeps each user): a card that
fails for any reason rolls back alone, is logged and leaves the queue. Tests: `test_recall_pg.py::test_a_hostile_text_or_time_breaks_neither_the_cards_nor_the_search`
(Postgres; red without the text cleaning) and `test_recall.py::test_one_card_failing_leaves_the_other_cards_built`
(a numeric text, and a card failing in a way nobody foresaw; red without the SAVEPOINT and without the type check).
`task_summary.first_user_query` also read a non-string text as a crash; it is skipped now (the member's own write
answered 500).

**4. A message time far in the future** (`telemetry_service.message_ts`). The backfill and the live write stored a
message's `ts` as sent. A card's last time is its task's last message time, and the recall search turns it into a
date: a time past the year 9999 failed every search that found the card and every read of it, for each member of an
organization project who can see it. A float or string time failed the sender's own write. Only a whole number of
milliseconds in 0..2100-01-01 (`MESSAGE_TS_MAX`, the bound the error report and exchange schemas use) is a time now;
any other value is stored as no time (the message appends, like one without a `ts`). Test: the recall test above (red
without the bound: the search answers 500).

**5. No body limit on `POST /api/events`** (`routers/events.py`). A single event was read whole, parsed and serialized
again with no limit: one request with a 100 MB model id took about a gigabyte of the API's memory (strings audit), and
a few concurrent ones could have it killed. Both event routes now use `_CappedRoute`, which refuses a body above
`BACKFILL_MAX_BYTES` (50 MiB) with 413 before it is read whole; the backfill route's own cap became that route class.
A real event is at most one message of a conversation (the largest live `Task Message` event is 3.7 MB), and a
conversation upload already had this cap. Test: `test_backfill_size_cap.py::test_an_event_over_the_cap_is_413` (red
with the plain route class, together with the backfill cap tests).

**6. One account's bridge events could hold the whole pool** (`realtime/sio.py`). socket.io runs every event in a task
of its own, and each message event took a pooled database session; the HTTP rate limit does not cover the socket.io
mount. A client emitting events faster than they are written held every connection of the pool (30), and every other
account's requests waited up to the pool timeout. Every bridge session of an account now goes through
`_user_session`, which allows `USER_SESSIONS_MAX` (8) at once. Past them an event waits for a session of its own
account (a per-account semaphore), so a burst of parallel subtasks finishing at once loses no message: their saves
also wait for each other on the run's ancestor rows, so eight in flight is reachable for a real client. Past
`USER_WAITING_MAX` (64) waiting events of one account the event is dropped (`BridgeBusy`, which the save logs like any
failed write, and a browser's join is refused), so a flood neither holds the pool nor queues without bound. Test:
`test_bridge.py::test_one_account_holds_at_most_its_share_of_the_sessions`, red both when the ninth event is dropped
instead of waiting and when nothing is ever dropped.

**7. Breakdown tables of any length** (`web/presenters/charts.breakdown`). The metrics page listed every model, mode,
provider and client name of the period. Phase 1 cuts a name to 256 bytes, but one organization member sending
thousands of distinct names still made the admin's page as long as they pleased (20,000 names: 14 MB of HTML). A
table now shows the 50 biggest rows and sums the rest into one "N others" row, as the ranked charts beside them
already did with 8. Test: the end-to-end test below.

**8. Absurd usage in a recorded exchange** (`schemas/llm_exchange.py`). The usage figures were finite floats with no
range, and `sequence` an unbounded integer for an INTEGER column, so an exchange with 1e300 tokens or a sequence of
2^31 answered 500 instead of 422 (only the sender's own dataset is affected). The usage figures now carry phase 1's
bounds of one request and `sequence` the column's range. Test: `test_llm_exchanges.py::test_broken_bodies_are_refused`
(red without the bounds).

**Migration `f1b2c3d4e5a6`** clears what the code above refuses from now on, stored before it: message times outside
0..2100 become NULL, their tasks' first and last times are taken again (as `refresh_task_summary` takes them, a
resume excluded) and a card with a last time outside the range takes its task's; a parent link between two accounts'
tasks is cut. Run totals do not change (a run never counted another owner's task). On the live deployment no row is
affected (read-only SELECTs: message times between 1789145185030 and 1793140662903, no link across owners). Test:
`test_migration_drift.py::test_hostile_client_data_is_cleared`.

**End to end:** `tests/test_hostile_clients.py`, on SQLite and on Postgres (`RECALL_PG_URL`). An organization member
sends, through `POST /api/events`, `/api/events/backfill` and the real ingest code: completions with 5e18 tokens,
costs of 1.5e308 and -1000, durations past int64, model, mode and kind names with a NUL, a lone surrogate, 3,000
characters, a number and an object, 60 distinct model names; messages with 9e18 tokens, a cost of 1e300, a time of
9e18, a float time, a NUL and a numeric text; a subtask link; a completion and two links naming another account's
task. Then the admin's organization metrics page answers 200 for every grouping, with totals that count exactly the
admin's request and the member's 60 bounded ones, every model name under 256 bytes and the breakdown folded; the
other account's list shows its run, with no parent, no models label and its `updated_at` untouched; and the
member's own list (grouped and flat), task page, metrics (own and organization) and problem report answer 200.
Mutations: the breakdown fold dropped, the owner condition dropped from `record_relation`: both red.

## Not done, with the reason

- **A removed member keeps adding to the organization's metrics.** The organization page counts every completion on
  the organization's tasks by their owner, so an account removed from the organization can still send figures (each
  bounded by phase 1) for its old tasks there. Counting an event only under the organization claim it was sent with
  (`telemetry_events.organization_id`) would close it, but it changes what a mid-task switch of organization counts,
  and the metrics rollup branch would need the organization in its key. An owner decision.
- **The organization's quality panel reads every run of the period.** Its rows are counts the server derives, one per
  root task, and grading them is Python (`session_quality.quality_of`); the cost grows with the organization's tasks,
  which a member creates one bridge write at a time (now at most eight at once per account). Grading in SQL is a
  separate change to measure first.
- **Text Postgres cannot hold in a title, a tool path or a workspace path.** A first message or a tool call with a NUL
  makes the sender's own write fail (its title or path is stored as text). Only the sender's own data is affected.

## Tests

The tests named above, run on SQLite and with the Postgres lane. The existing tests changed where the behaviour
changed: `record_relation` takes the sender everywhere; the random walk of the run totals sends every link from
either account (links across owners are refused, so its opening no longer builds one); the route table names
`_CappedRoute` for the two event routes. Full suite at the top of the stack (`feat/web-metrics-rollup`, on phases 1 to 4, the hostile-client bounds and the session settings), with the Postgres lane (`RECALL_PG_URL`): 1585 passed, 1 xfailed.

## Deploy

The migration runs with the others (`db-migrate.sh`); on the live data it changes nothing. The api image picks the
code up on start.
