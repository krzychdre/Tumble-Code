# VSIX never ships a .env file

**Status:** done.
**Related plans:** `2026-10-23_17-20_maintenance-audit-round-4.md`, `2026-10-24_16-00_r4-drop-dotenvx.md`.
**Touched:** `src/.vscodeignore`, `apps/vscode-nightly/esbuild.mjs`, `.github/workflows/marketplace-publish.yml`.

## Problem

`src/.vscodeignore` re-included `.env` ("for telemetry", a PostHog leftover; telemetry is cloud-only since #745),
and the nightly build copied `src/.env` into its package. A VSIX built on a machine with a local `src/.env` would
ship whatever keys that file holds. The release workflow's sanity check `grep -q ".env"` looked for a `.env` in the
package but only matched by accident (the regex `.env` hits icon names such as `folder-environment.svg`).

## Change

- `src/.vscodeignore`: the `!.env` include is gone, so the leading `**` excludes the file.
- `apps/vscode-nightly/esbuild.mjs`: the nightly build no longer copies `../.env`.
- `marketplace-publish.yml`: the check is inverted; packaging fails when the VSIX lists any `.env` file.

The extension still loads an optional `.env` in development (`loadOptionalEnvFile`, #1033); a missing file is not
an error, so a released extension behaves the same.

## Tests

- With `FAKE_KEY=should-not-ship` in `src/.env`, `pnpm vsix` and `pnpm vsix:nightly` both produce packages with no
  `.env` entry; the other required entries (`package.json`, `dist/extension.js`, the webview `index.js`) are there.
- The new check passes on that VSIX and fails on a copy with `extension/.env` added (mutation).
