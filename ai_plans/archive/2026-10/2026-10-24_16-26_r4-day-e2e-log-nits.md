## Problem

1. `initializeSourceMaps` added a `<link rel="preload">` for five guessed names per script (`index.js.map` twice,
   `index.js?source-map=true`, `index.map.json`, `index.sourcemap`) and fetched the whole script again to preload
   its `sourceMappingURL` (the same `index.js.map`). The guessed names do not exist, so the webview console logged
   failed loads. The build always writes `<name>.js.map` next to the script (vite `build.sourcemap`, and
   `sourcemapPlugin` adds the `sourceMappingURL` comment for that name).
2. `[CustomModesManager] Failed to load modes ... custom_modes.yaml: ENOENT` on a fresh profile. Cause, reproduced
   with real files: `getCustomModesFilePath` creates the missing file through `queueWrite`, and `queueWrite` returns
   at once when another write is already running (the operation only joins the queue). Activation starts the file
   watcher (one creation) while the first state push reads the modes (a second one, which returns before any file
   exists), so `loadModesFromFile` reads a file that is not there yet.

## Change

1. Preload exactly `${script.src}.map`; the guesses and the re-fetch of the script are gone.
2. `loadModesFromFile` returns `[]` for ENOENT without logging: no file is no modes, which is also what the queued
   creation writes. Other read errors (EACCES) and parse or schema errors are still logged. Making `queueWrite`
   await the caller's own write was tried and rejected: a write that calls `refreshMergedState` (for example the
   first project mode on a fresh profile) would then wait for a creation queued behind itself and deadlock
   (`CustomModesManager.exportImportSlugChange.spec.ts` timed out).

## Tests
