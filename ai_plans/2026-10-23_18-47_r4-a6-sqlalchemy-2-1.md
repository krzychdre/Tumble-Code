# R4 A6: SQLAlchemy 2.1 migration

**Status:** done

**Related plans:** [maintenance audit round 4](2026-10-23_17-20_maintenance-audit-round-4.md), item A6 (owner
decision: migrate now).

## Touched files

- `self-hosted-cloudapi/pyproject.toml`
- `self-hosted-cloudapi/uv.lock`

## Problem

The service floor `sqlalchemy>=2.0.36` let 2.1 in, and 2.1 is a feature release with its own migration notes.

## Change

`sqlalchemy[asyncio]>=2.1.6`, lock moved from 2.0.54 to 2.1.6. The `asyncio` extra is the one change the service
needs: 2.1 keeps greenlet only in that extra, and without it `uv lock` drops greenlet, which the async engine
(`create_async_engine`, `AsyncSession`, alembic's `async_engine_from_config`) cannot run without. No source change.

## 2.1 changes checked against the service

Source: "What's New in SQLAlchemy 2.1" (docs.sqlalchemy.org/en/21/changelog/migration_21.html).

| 2.1 change                                                             | Service usage                                                                        | Result               |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------- |
| greenlet only in the `[asyncio]` extra                                 | whole service is async                                                               | applied: extra added |
| Python 3.11 minimum                                                    | `requires-python >=3.12`, image 3.13                                                 | no action            |
| Default PostgreSQL driver is psycopg 3                                 | `database.py` rewrites the URL to `postgresql+asyncpg://`, alembic uses the same URL | no action            |
| Autoflush on every execution, Core and `text()` too                    | only `text("SELECT 1")` on a connection in the readiness probe, no session           | no action            |
| `Select.filter_by()` searches all FROM entities, ambiguous names raise | one call, `exchange_ingest.py`, single-entity select                                 | no action            |
| `ClauseElement.params()` deprecated                                    | no SQLAlchemy `params()` calls (the `params()` hits are our presenters)              | no action            |
| Mapped dataclass defaults, `exclude_properties`, composites            | not used                                                                             | no action            |
| Loader options from a deeper path                                      | one `selectinload(Membership.organization)`, no overlapping paths                    | no action            |
| Named types (Enum, DOMAIN) bound to MetaData                           | no Enum or DOMAIN columns                                                            | no action            |
| `Row` typed without `Tuple`, float literals in CAST                    | no `Row` annotations, one `cast(..., Integer)`                                       | no action            |
| cursor-execute event error handling                                    | `before_cursor_execute` listeners only in tests, they record statements              | no action            |

## Tests

- Full `uv run pytest -q -W error::sqlalchemy.exc.SADeprecationWarning`: 1345 passed, 1 xfailed, no SQLAlchemy
  deprecation warning.
- Throwaway PostgreSQL 16.15 container: `db-migrate.sh` classifies FRESH, runs create_all and `alembic stamp head`;
  `alembic check` reports no new upgrade operations; a second `db-migrate.sh` run (MANAGED, `alembic upgrade head`)
  is clean.
- Throwaway `docker build`: the image imports SQLAlchemy 2.1.6 and greenlet 3.5.6. Image deleted afterwards.
- Without the `[asyncio]` extra, `uv lock` removes greenlet (seen while locking 2.1.6), which is what the extra
  guards against.

## Notes

`alembic downgrade` from head on a create_all database fails at `a7b8c9d0e1f2` (constraint
`fk_tasks_parent_task_id` does not exist, because create_all names the foreign key differently). This happens on
SQLAlchemy 2.0.54 too and is not part of this change. The live api image is not rebuilt here; the owner rebuilds it.
